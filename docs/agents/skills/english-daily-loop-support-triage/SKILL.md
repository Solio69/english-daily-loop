# Разбор отчётов поддержки English Daily Loop

## Назначение

Разбирать пользовательские отчёты об ошибках в `english-daily-loop`. До явного запроса пользователя на исправление кода проводить только read-only анализ и диагностику.

## Обязательный контекст проекта

Перед диагностикой прочитать актуальную проектную документацию, если она есть в репозитории:

- `AGENTS.md`
- `notes/support-diagnostics.md`
- `notes/ai-observability-diagnostics.md`, если отчёт содержит AI-диагностику
- `notes/security-threat-model.md`, если отчёт затрагивает auth, secrets, доступ или раскрытие данных БД

## Правила безопасности

- Не применять миграции и не изменять данные БД.
- Перед любым разбором production-данных явно сообщить пользователю: `Мы работаем с production БД`.
- Не просить пользователя присылать Telegram `initData`, токены, необработанные ответы провайдера, полные prompts, полные сгенерированные тексты или secrets.
- Использовать только read-only SQL.
- Считать `public.support_reports` чувствительными операционными данными. Цитировать в ответе только релевантные поля.
- Не выводить `user_id` или `telegram_user_id`; внутренний `user_id` допустим только внутри server-side `join` и не должен присутствовать в `select`.
- Не использовать `select *`, не выгружать полный diagnostic snapshot и не копировать полные `events`, `app_context` или пользовательский комментарий в долговременную документацию.
- Если доступа к БД нет, передавать владельцу по одному запросу из `references/sql.md`, ждать минимальный безопасный результат текущего шага и только затем выбирать следующий запрос.

## Порядок разбора

1. Определить наличие отчётов.
   - Начать только с количества и диапазона дат.
   - Если отчетов нет, завершить проверку без дополнительных запросов.

2. Выбрать отчёт.
   - Получить минимальный список без пользовательских идентификаторов, полных событий и полного app context.
   - Выбрать конкретный `support_reports.id` в scope.
   - Тестовые и явно исключенные записи дальше не раскрывать.

3. Изучить только необходимое содержимое выбранного отчёта.
   - Проверить релевантные `user_comment`, `current_screen`, `created_at`, release metadata, `request_ids`, безопасные `ai_diagnostics` и отфильтрованные `events`.
   - Считать пользовательский комментарий потенциально чувствительным и не цитировать личные данные.
   - Не запрашивать полный `app_context`, полный prompt, raw provider response или generated content.

4. Определить вероятную область проблемы.
   - Auth/bootstrap: `auth-telegram`, отсутствующий или просроченный initData, сводка роли/подписки.
   - Генерация текста: `generate-reading-text`, OpenRouter, валидация, сохранение active text.
   - Словарные карточки: `prepare-vocabulary-cards`, ответ провайдера, валидация результата, сохранение карточек.
   - Повторение: `get-vocabulary-review-state`, `review-vocabulary-word`, счётчики и completion markers.
   - Клиентский UI/state: события экранов, повторная навигация, устаревшее состояние, ошибки модальных окон и форм.
   - Локальная инфраструктура: доступность tunnel/API, устаревшая сборка функции, неприменённая миграция.

5. Сопоставить доказательства.
   - Использовать `request_ids` для поиска в логах Edge/API.
   - Использовать `ai_diagnostics` для безопасной проверки stage/model/promptVersion.
   - Для ошибок AI использовать таблицы попыток:
     - `public.reading_generation_attempts`
     - `public.vocabulary_card_generation_attempts`

6. Сформулировать краткий диагноз.
   - Начать с вероятной причины.
   - Привести доказательства с названиями полей и датами.
   - Отделить подтверждённые факты от гипотез.
   - Предложить минимальное безопасное исправление или следующую проверку.

7. Присвоить ровно одну классификацию и маршрут.
   - `тест / шум`: действий не требуется; не раскрывать дополнительные поля.
   - `дубликат`: использовать существующую bug-карточку или feature draft, не создавать второй элемент.
   - `внешний инцидент`: зафиксировать диагноз и восстановление; не менять код без подтвержденного дефекта приложения.
   - `наблюдаем`: данных недостаточно; передать кейс в bug dashboard со статусом `наблюдаем`.
   - `bug`: передать в канонический skill `docs/agents/skills/triage-english-daily-loop-bugs/SKILL.md` для поиска дубликата, карточки и согласуемой баг-пачки.
   - `improvement / feature`: передать в канонический skill `docs/agents/skills/english-daily-loop-feature-spec/SKILL.md` и создать или обновить feature draft.

8. Минимизировать долговременные данные.
   - Сохранить только report id, дату, безопасный краткий пересказ и минимальные доказательства.
   - Не копировать полный комментарий, events, app context, generated content или идентификаторы пользователя.
   - Actionable evidence переносить сразу: исходные support reports удаляются retention job через `30` дней.
   - Не изменять строку отчёта и не вести отдельный реестр processing-статусов.

## SQL-справочник

Для read-only запросов прочитать `references/sql.md`. Выполнять запросы по одному: от count/date summary к минимальному списку, затем только к конкретному report id. Использовать только запросы, необходимые для текущего отчёта.

## Формат ответа

Использовать следующую структуру, если пользователь не запросил другой формат:

- **Что видно:** краткое описание подтверждённых фактов.
- **Вероятная причина:** одна или две наиболее вероятные причины.
- **Доказательства:** поля отчёта, request ids, AI stage/model и релевантные строки попыток.
- **Классификация:** ровно одна из `тест / шум`, `дубликат`, `внешний инцидент`, `наблюдаем`, `bug`, `improvement / feature`.
- **Маршрут:** действие или канонический workflow; для дубликата — существующий элемент.
- **Что проверить дальше:** минимальный набор следующих проверок.
- **Что править:** предлагаемое изменение кода, конфигурации или документации, если доказательств достаточно.
