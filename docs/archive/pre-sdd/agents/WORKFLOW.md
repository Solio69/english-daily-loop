# Рабочий процесс проекта

## 1. Назначение

Этот документ описывает единый рабочий процесс `english-daily-loop` для владельца проекта и AI-агентов: от первичного обсуждения задачи до реализации, проверок и передачи результата на ручное тестирование.

Документы распределяют ответственность следующим образом:

- `AGENTS.md` — обязательные правила работы в репозитории, технические ограничения и требования безопасности;
- `GIT_POLICY.md` — обязательная read-only политика Git для AI-агентов;
- `docs/agents/WORKFLOW.md` — источник истины о жизненном цикле задач;
- project-local skills в `docs/agents/skills` — специализированные процедуры для фич, багов и support reports;
- согласованная спецификация или баг-пачка — источник истины о scope и ожидаемом поведении конкретной задачи.

При противоречии ограничения из `AGENTS.md` и `GIT_POLICY.md` имеют приоритет. Неясность или противоречие нельзя закрывать предположением: работу нужно остановить и запросить решение владельца.

## 2. Роли и ответственность

### Владелец проекта

Владелец проекта:

- определяет продуктовую цель и принимает решения о пользовательском поведении;
- выбирает вариант при наличии значимых компромиссов;
- согласовывает scope, дизайн, acceptance criteria и спецификацию;
- дает допуск к реализации;
- выполняет действия, которые запрещены агенту: установку сторонних пакетов и ПО, применение миграций, изменение данных БД, deploy и изменяющие Git-команды;
- выполняет ручные проверки, отмечает checklist и присваивает итоговый статус `проверено`.

### AI-агент

AI-агент:

- исследует актуальные код, документацию и разрешенный read-only Git-контекст;
- задает вопросы, на которые нельзя надежно ответить из проекта;
- предлагает обоснованные варианты решения и рекомендует один из них;
- объясняет frontend, server и database-части простыми техническими формулировками;
- готовит или уточняет спецификацию;
- изменяет код только после допуска к реализации;
- выполняет доступные автоматические проверки;
- сверяет результат со спецификацией и проводит pre-commit review;
- передает владельцу понятные следующие действия и одно название коммита в формате, удобном для копирования.

## 3. Ограничения проекта

`english-daily-loop` разрабатывает и обслуживает один разработчик без отдельной команды DevOps, QA и поддержки. Время на разработку и сопровождение ограничено, а регулярные денежные расходы должны оставаться минимальными.

При выборе решения:

- учитывать не только прямую цену, но и время внедрения, регулярное обслуживание, сложность диагностики и восстановления;
- по умолчанию выбирать самое простое обратимое решение, которое обеспечивает требуемые безопасность, надежность и качество;
- отдавать предпочтение существующему стеку и управляемым сервисам, если они уменьшают операционную нагрузку без неоправданной стоимости и lock-in;
- добавлять платные сервисы и автоматизацию, когда экономия времени или снижение подтвержденного риска оправдывают стоимость;
- не внедрять enterprise-процессы и инфраструктуру до появления соответствующих требований или нагрузки;
- проектировать небольшие итерации, которые можно проверить и при необходимости расширить;
- отдельно указывать владельцу разовые затраты, регулярные расходы и ожидаемое время сопровождения каждого значимого варианта.

Ограничение бюджета не является основанием ослаблять контроль доступа, хранить секреты небезопасно, отказываться от проверяемых бэкапов или принимать риск потери пользовательских данных без явного решения владельца.

### Backlog проекта

Фраза владельца `добавим задачу` без указания другого места означает:

1. Открыть `D:\anastasiaStorage\Проекты\Разработка English daily loop.md`.
2. Проверить, что такой или эквивалентной незавершенной задачи еще нет.
3. Добавить в раздел `**Все подряд**` одну короткую и понятную строку в существующем формате списка.

Без прямого указания владельца нельзя создавать или изменять задачи в TickTick, GitHub Issues и других внешних task managers. Явно указанное владельцем другое место или формат имеет приоритет над этим правилом.

Формулировка backlog-задачи должна описывать ожидаемое действие или результат без технических подробностей, секретов и чувствительных данных. Детальный контекст хранится в соответствующей локальной спецификации или проектной документации.

## 4. Выбор рабочего маршрута

Перед началом работы определить тип запроса.

### Новая фича или несогласованное улучшение

Использовать `docs/agents/skills/english-daily-loop-feature-spec`.

Код приложения не изменяется во время груминга. Каноническая спецификация создается в `D:\anastasiaStorage\pet-projects\English daily loop\Фичи`.

### Сырой отчет о баге

Использовать `docs/agents/skills/triage-english-daily-loop-bugs`.

Сначала подтвердить наблюдаемое и ожидаемое поведение, классифицировать проблему и подготовить согласуемую баг-пачку. До статуса `готово к разработке` код приложения не изменяется.

### Согласованная спецификация или баг-пачка

Кодинг-агент полностью читает документ, сверяет его с актуальными кодом, документацией и Git HEAD и проверяет готовность к реализации. После успешной проверки работа продолжается по разделу «Реализация».

### Support report

Использовать `docs/agents/skills/english-daily-loop-support-triage`.

Support triage ограничивается безопасной диагностикой и не дает автоматического допуска к исправлению кода.

### Явно запрошенное изменение без отдельной спецификации

Владелец может явно попросить выполнить конкретное изменение без отдельной спецификации. Такой запрос является допуском только для указанного scope.

Прямой переход к реализации допустим, если одновременно выполняются условия:

- ожидаемое поведение однозначно;
- нет открытых продуктовых, архитектурных или дизайн-решений;
- понятны границы изменения и критерии проверки;
- не требуется расширять scope;
- соблюдаются ограничения `AGENTS.md` и `GIT_POLICY.md`.

Если любое условие не выполняется, сначала требуется обсуждение или спецификация.

## 5. Общий жизненный цикл задачи

### Шаг 1. Понять задачу и контекст

До предложения решения:

1. Зафиксировать цель, проблему и ожидаемый пользовательский результат.
2. Изучить относящиеся к задаче документацию, код, типы, тесты, миграции и read-only Git-контекст.
3. Отделить подтвержденные факты от предположений.
4. Запросить недостающую информацию, если ответ нельзя надежно получить из проекта.

Запрещено придумывать продуктовые требования, состояние внешних систем, содержимое данных или технические ограничения.

### Шаг 2. Согласовать пользовательский flow

До технического проектирования описать:

- точку входа пользователя;
- основные действия и состояния интерфейса;
- успешный результат;
- loading, empty и error states;
- повторные действия, восстановление и навигацию;
- влияние на существующие сценарии.

Для пользовательских изменений UI необходимо прочитать `docs/agents/DESIGN_SYSTEM.md`. Изображение или визуальный вариант изменения готовится по запросу владельца и должен соответствовать дизайн-системе.

### Шаг 3. Рассмотреть варианты

Если решение содержит значимый выбор, предложить не менее двух реалистичных вариантов. Для каждого кратко описать:

- принцип работы;
- преимущества;
- недостатки и риски;
- влияние на безопасность, стоимость, поддержку и vendor lock-in, когда это применимо.

После сравнения дать рекомендацию и объяснить критерии выбора. Для очевидного локального изменения искусственные альтернативы не требуются.

### Шаг 4. Согласовать технический подход

До подготовки финальной спецификации объяснить:

- какие frontend-слои меняются;
- какая логика остается на сервере;
- какие таблицы, поля, RPC или миграции затрагиваются;
- как сохраняются auth, RLS, grants и границы доступа;
- какие ошибки и диагностические данные ожидаются;
- какие автоматические и ручные проверки подтверждают результат.

Бизнес-логика и UI не смешиваются без необходимости. Доступ к данным изолируется в сервисном слое, общие доменные типы размещаются в `src/types`, а чувствительные проверки выполняются на сервере.

### Шаг 5. Подготовить спецификацию

Спецификация должна описывать актуальное целевое состояние задачи и включать:

- цель и пользовательскую ценность;
- scope и явно исключенный scope;
- согласованный пользовательский flow;
- дизайн и состояния UI, если применимо;
- frontend, server и database-контракты;
- требования безопасности и приватности;
- обработку ошибок и наблюдаемость;
- нумерованный план реализации;
- наблюдаемые acceptance criteria;
- автоматические проверки;
- подробный ручной checklist по `docs/agents/references/manual-testing-guide.md`;
- риски, зависимости и действия владельца;
- отсутствие открытых решений либо их явный перечень.

Документация и спецификации описывают текущее состояние. Формулировки истории изменений в стиле `было → стало` используются только в явно запрошенном changelog.

### Шаг 6. Проверить готовность к разработке

Спецификация или баг-пачка готова к реализации, когда:

- scope и ожидаемое поведение согласованы владельцем;
- выбран технический подход;
- нет противоречий и открытых решений;
- acceptance criteria наблюдаемы и проверяемы;
- ручные сценарии покрывают критические и затронутые регрессионные пути;
- миграции, данные, auth, RLS, grants, secrets и внешние зависимости описаны явно;
- действия владельца отделены от действий агента;
- документ имеет статус `готово к разработке`.

Статус `готово к разработке` является продуктовым допуском в пределах согласованного scope.

### Шаг 7. Реализация

Перед изменением кода кодинг-агент:

1. Полностью читает согласованный документ.
2. Сверяет его с актуальными кодом, документацией и Git HEAD.
3. Проверяет отсутствие новых противоречий и технических блокеров.
4. Для баг-пачки или спецификации ставит статус `в разработке`.
5. Добавляет технический план, если он предусмотрен форматом документа.

Реализация выполняется небольшими проверяемыми изменениями с сохранением структуры и стиля проекта. Согласованный план можно выполнять без повторного подтверждения, пока решение остается внутри утвержденного scope.

### Шаг 8. Условия обязательной остановки

Агент останавливает реализацию и запрашивает решение владельца, если:

- требуется изменить согласованный scope или пользовательское поведение;
- обнаружено противоречие в спецификации;
- требуется несогласованный дизайн;
- необходима несогласованная миграция или изменение данных;
- меняются auth, RLS, grants или другие границы безопасности сверх согласованной задачи;
- нужны действия с секретами;
- требуется установить сторонний пакет или ПО;
- обнаружен технический блокер, который нельзя безопасно устранить в текущем scope.

Остановка должна содержать подтвержденные факты, влияние на задачу и доступные варианты продолжения.

### Шаг 9. Автоматические проверки

После реализации агент:

1. Сверяет изменения с каждым применимым acceptance criterion.
2. Запускает проверки, соответствующие затронутому scope.
3. После существенных изменений запускает минимум `pnpm lint`.
4. Для изменений повторения, навигации и общих frontend helpers запускает `pnpm test`.
5. При необходимости запускает дополнительные существующие проверки без установки новых зависимостей.
6. Сообщает точные результаты и явно перечисляет проверки, которые выполнить не удалось.

### Шаг 10. Pre-commit review

Агент проводит review всего затронутого scope:

- проверяет корректность, простоту и соответствие архитектуре;
- ищет регрессии, граничные случаи и расхождения со спецификацией;
- проверяет безопасность, приватность и server-side границы;
- проверяет тестовое покрытие и понятность документации;
- отделяет обязательные исправления от необязательных улучшений;
- исправляет найденные проблемы внутри согласованного scope;
- предлагает дополнительные улучшения проекта и кратко объясняет пользу и риски каждого.

Git при review используется только в read-only режиме согласно `GIT_POLICY.md`.

### Шаг 11. Передать результат владельцу

Итоговый отчет содержит:

- что реализовано;
- соответствие спецификации и acceptance criteria;
- результаты автоматических проверок;
- найденные риски и предложения по улучшению;
- следующие действия владельца в правильном порядке;
- назначение каждой необходимой команды;
- одно название коммита на английском для всего scope.

Формат названия коммита:

- `fix: ...` — исправление бага;
- `feat: ...` — новый пользовательский или технический функционал;
- `refactor: ...` — улучшение существующей реализации без нового поведения;
- `tech: ...` — изменение конфигурации или технической инфраструктуры;
- `chore: ...` — вспомогательная или нерегулярная работа.

Название коммита выводится в отдельном fenced code block, чтобы интерфейс показывал кнопку копирования. В блоке должна находиться только одна строка названия без `git commit -m`, кавычек и пояснений.

Пример:

```text
feat: add vocabulary review flow
```

После реализации и успешных автоматических проверок документ получает статус `готово к ручной проверке`. Только владелец отмечает пункты ручного checklist и ставит статус `проверено`.

## 6. Статусы

| Статус | Значение | Кто устанавливает |
| --- | --- | --- |
| `черновик` | Требования и решения уточняются | Агент, ведущий grooming или triage |
| `черновик для согласования` | Документ готов к рассмотрению владельцем | Агент, ведущий grooming или triage |
| `готово к разработке` | Scope и критерии согласованы, реализация разрешена | Агент после явного согласия владельца |
| `в разработке` | Кодинг-агент проверил актуальность документа и начал реализацию | Кодинг-агент |
| `готово к ручной проверке` | Реализация и доступные автоматические проверки завершены | Кодинг-агент |
| `проверено` | Владелец успешно выполнил ручной checklist | Только владелец |

Специализированный skill может добавлять промежуточные статусы, но не меняет смысл основных контрольных точек.

## 7. Ограничения выполнения

### Сторонние пакеты и ПО

AI-агент не скачивает и не устанавливает сторонние пакеты или ПО. Если зависимость действительно требуется, агент объясняет необходимость, риски и передает владельцу подходящую команду.

### Локальная база данных

AI-агент не применяет миграции и не выполняет команды, изменяющие данные даже в локальной БД. Необходимые локальные действия передаются владельцу с назначением команды и ожидаемым результатом.

Если реализация добавляет локально непримененную migration, до передачи задачи
на ручную проверку AI-агент обязан:

1. Явно сообщить, что migration еще нужно применить к локальной БД.
2. Передать владельцу точную команду `pnpm exec supabase migration up` и
   объяснить, какие migration она применит и что reset локальных данных не
   выполняется.
3. Явно ответить, требуется ли после этого перезапуск `npm run dev:telegram`,
   и объяснить причину.
4. В пошаговом режиме дождаться вывода владельца перед следующим действием.

Применение только SQL migration обычно не требует перезапуска уже работающего
`dev:telegram`: локальная БД обновляется сразу. Один полный перезапуск требуется,
если в scope добавлена новая Edge Function в явный список
`scripts/dev/config.mjs`, изменены `.env.telegram.local`, `vite.config.ts`,
dependencies либо завершился обязательный процесс dev-stack. Изменения
frontend-кода подхватывает watcher, а изменения кода уже запущенных Edge
Functions — локальный function runner; в этих случаях полный перезапуск не
нужен.

### Production БД

При любой задаче, относящейся к production БД, агент явно сообщает: `Мы работаем с production БД`.

Агент ограничивается безопасным анализом, подготовкой кода миграции или документации. Агент не выполняет и не передает владельцу команды, способные изменить production БД, включая миграции, DDL, DML, reset, seed и административные операции.

### Git

AI-агент использует Git только для чтения. Полный перечень правил находится в `GIT_POLICY.md`.
