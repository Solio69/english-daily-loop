# Разбор багов English Daily Loop

## Источники и размещение

Прочитай `AGENTS.md`, `GIT_POLICY.md`, релевантные `notes/`, [дизайн-систему](../../../docs/DESIGN_SYSTEM.md) для UI и актуальный код/тесты. Общая структура Obsidian: `D:\anastasiaStorage\Проекты\English daily loop\_English daily loop.md`; незавершённые карточки: `_project inbox/`, подготовка выбранной работы: `_work/`. Не используй архивные пути `pet-projects/English daily loop/Баги` и блок «Все подряд» как действующие источники. Если структура на диске отличается, проверь её и уточни маршрут вместо создания дубля.

## Разбор

1. Сохрани исходное наблюдение и найди возможные дубликаты по сценарию и ожидаемому результату, а не только заголовку. Репозиторий и Git на этапе triage исследуй в режиме чтения. Не меняй продуктовый код и данные БД.
2. Проверь текущее поведение, область кода, среду, безопасные доказательства, частоту и обходной путь. Отделяй подтверждённое от гипотез. Классифицируй как bug, improvement, feature, ops либо observing. Влияние critical/high/medium/low оценивай по фактам; приоритет выбирает владелец.
3. Для дефекта или небольшого совместимого улучшения создай/обнови одну карточку в `_project inbox/` по [шаблону](references/bug-card-template.md), добавь ссылку в раздел `Входящие задачи` главного файла только если её ещё нет и пользователь поручил зарегистрировать работу. Не добавляй самовольно в дневной план или TickTick. Для feature или изменения продуктового контракта передай контекст в [груминг фичи](../english-daily-loop-feature-spec/SKILL.md).
4. Вопросы о поведении, дизайне, данных и границах задай пользователю. Не заполняй его решения по догадке. После ответов обнови карточку актуальным целевым решением. Несвязанные баги не объединяй ради крупной пачки; связанные можно кратко сгруппировать по [шаблону](references/batch-template.md) в `_work/`, сохранив ссылки на исходные карточки.
5. Перед запуском SDD на выбранную единицу работы подготовь компактный обзор с вариантами исправления и проверяемым результатом по общему [грумингу](../english-daily-loop-feature-spec/SKILL.md). После согласования обзора и назначения ветки агент проходит полный Spec Kit, анализ и реализацию без второго допуска. Текущий HEAD и затронутые контракты проверь повторно перед техническим планом.

Подробные ручные сценарии оформляй по [руководству](../../references/manual-testing-guide.md); отметки о фактической ручной проверке ставит владелец. Не выполняй миграции, изменение данных, PR и выпуск. Git-полномочия определяет только корневой `GIT_POLICY.md`.
