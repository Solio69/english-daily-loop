# Правила написания кода English Daily Loop

Эти правила адаптированы из `green-api-chat/docs/CODING_RULES.md` к текущему стеку Vite, React, TypeScript, Tailwind CSS и Supabase. Они задают критерии ревью будущих изменений. Проверки типов, ESLint, Prettier и Stylelint запускаются отдельными командами из `package.json`; охват исторического кода и baseline описаны в [руководстве проверок](../references/quality-checks.md).

## Границы модулей и данные

- Предпочитай существующие компоненты, сервисы и типы новым уровням абстракции. Не смешивай UI с бизнес-правилами, запросами к данным и проверкой доступа. К серверным данным обращайся через существующий сервисный слой; Edge Functions отвечают за доверенную проверку Telegram `initData`, валидацию, лимиты и запись через разрешённый серверный контракт.
- Общие доменные типы держи в `src/types`, локальные типы рядом с владельцем. Не дублируй контракт frontend/Edge Function/SQL в расходящихся вариантах. Внешние и AI-данные валидируй на границе до использования.
- Не переноси server-only секреты, `service_role`, Telegram token, полные prompts и личные данные во frontend, URL и логи. RLS, grants и права роли проверяй по соответствующей спецификации. Сложные конкурентные операции и изменение нескольких связанных записей выполняй атомарно через существующие RPC/транзакционные механизмы, когда это требуется контрактом.

## Компоненты, функции и импорты

- Давай компоненту и обработчику имя по действию. Обработчик с логикой объявляй до JSX и передавай по имени. Для короткого выражения предпочитай лаконичную стрелочную функцию; методы, генераторы и API со специальной сигнатурой сохраняют нужную им форму. Не превращай технический стиль в массовую правку нетронутого кода.
- Собственные функции приложения, тестов и конфигурации объявляй именованными стрелочными через `const`, когда контракт не требует иной формы. Методы с существенным `this`, генераторы, перегрузки и сторонние API сохраняют необходимую сигнатуру; исключение объясняй при ревью.
- Если у собственной функции больше одного аргумента, передавай объект с именованными полями. Браузерные, React, Supabase и другие внешние API сохраняют их сигнатуры.
- Если условие содержит несколько сравнений, дай всему условию смысловое имя перед `if`. Для одной короткой ветки с `return` допускается форма без блока; для нескольких действий оставляй блок. Длинные ветки оформляй через `if` или `switch`, вложенные тернарники не используй. Выражение `&&` применяй только когда сохранение `false`, `0` или пустой строки в результате допустимо; для отсутствующего JSX-атрибута возвращай `undefined`.
- Используй действующий alias и структуру `tsconfig.json`: `@/*` сейчас указывает на корень репозитория, а не на `src`. Не копируй импортные ограничения Next.js. Импорты группируй последовательно и не создавай циклических зависимостей. Не используй `any` для обхода непроверенного входа; типы должны выражать контракт, а приведение типа требует основания.
- Не оставляй мёртвый код, неиспользуемые импорты и фиктивные заглушки.

## Обязательное правило: значения в константах и фикстурах

- Не пиши строковые и числовые значения непосредственно в месте использования — ни в приложении, ни в тестах. Это относится и к однократным значениям: `status: 500`, `message: 'ошибка'`, `calls += 1`, `assert.equal(status, 401)` недопустимы.
- Переиспользуемые значения и контракты определяй один раз в смысловых константах или типах и импортируй там, где они нужны. Это касается HTTP-методов, статусов, заголовков, кодов и сообщений ошибок, лимитов и других общих данных. Не создавай отдельный псевдоним одного и того же значения в каждом файле.
- Данные и ответы для тестов храни в моках (`tests/mocks/` и, для Deno, рядом с тестами в `test-mocks.ts`). Если данные нужны только одному сценарию, определи отдельный мок этого сценария: именно в определении мока находятся его исходные строковые и числовые значения. Общие тестовые контракты держи в `tests/fixtures/`. В тестовом действии и ожидании используй мок либо общие константы. Не собирай моковый ответ из литералов внутри теста.
- Перед сдачей файла проверь тела функций и тестов: в местах использования не должны оставаться строковые, числовые и regex-литералы значений. Пути импортов, названия тестов и ключи объектов — синтаксис, а не данные сценария. При выносе значений не меняй тексты, поведение и управление потоком без отдельной причины.

## Целевой формат для следующего этапа

Prettier использует согласованные настройки: без завершающих `;`, два пробела, одинарные кавычки, завершающие запятые там, где поддерживаются, и LF. ESLint и Stylelint адаптированы к текущим TS/React и обычному CSS с Tailwind, без Next.js и SCSS-настроек источника. Изменяемый файл проходит новые проверки; массовую переформатировку существующего приложения не выполнять.

## Интерфейс и стили

- Следуй [дизайн-системе](../../docs/DESIGN_SYSTEM.md): Telegram mobile viewport, светлая и тёмная темы, доступность, понятные состояния загрузки и ошибок. Используй семантические элементы, подписи полей, управление с клавиатуры и видимый фокус. Не скрывай ошибки цветом без текста.
- Используй текущие Tailwind CSS v4 и CSS-переменные `src/index.css`. Не переноси SCSS Modules и токены Next.js-проекта. Общие цвета, размеры и интервалы выражай действующими семантическими переменными; новый стиль проверяй в обеих темах и мобильном окне.

## Тесты и проверка результата

- Для тестов действует правило констант и фикстур выше. Ожидания держи независимыми от реализации: не импортируй в ожидание ту же константу, из которой код берёт фактическое значение, иначе общая ошибка останется незамеченной. Сообщения о провале проверки формируй в общем assertion-helper. Тесты проверяют наблюдаемое поведение; не добавляй тест, который лишь повторяет реализацию.
- До коммита выполни проверки, перечисленные в `plan.md` и `tasks.md`, доступную проверку типов, релевантные тесты, сборку по риску и ручное ревью изменённых файлов. Ревью касается также тестов и вспомогательного кода. Отдельно сверяй спецификацию, staged diff, секреты, лишние файлы и выполнение критериев.
- Не отключай проверку типов через `@ts-nocheck` или `@ts-ignore`. Все Edge Functions должны проходить `pnpm test:edge`: проверку типов, Deno lint и тесты shared helpers.
- В `verification.md` фиксируй реальные команды и статусы Passed/Failed/Blocked/NotRun. Перед коммитом обязательные для данной части проверки должны быть успешны; перед передачей всей фичи проверяется интеграция частей.
