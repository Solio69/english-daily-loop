## Результат и границы

Чтение и подготовка карточек используют только OpenRouter и его встроенный model fallback. Приложение повторяет запрос только после успешного HTTP-ответа с пустым/невалидным содержимым, в конечном списке моделей и общем бюджете. Клиент получает безопасные метаданные, без произвольной строки провайдера, prompt, ответа модели, слов пользователя или ключа. Публичные понятные сообщения сохраняются.

## Критерии

- **AC-1:** 429/5xx, invalid provider JSON, сетевой сбой и timeout завершаются без прикладного повторного `fetch`; HTTP status/стадия остаются в безопасной диагностике.
- **AC-2:** успешный HTTP с пустым или предметно невалидным содержимым может повториться с оставшимися моделями; повтор конечен и не превышает текущие бюджеты: чтение 90 с, карточки 30 с суммарно.
- **AC-3:** диагностика ошибки чтения и карточек содержит лишь разрешённые ограниченные поля (функция, request ID, версия prompt, stage, длительность, проверенные счётчики и модель из allowlist, ограниченный provider status); не содержит `errorMessage`, произвольный `providerErrorCode`, исходные слова, prompt, ответ или секрет.
- **AC-4:** тесты с подставным `fetch` проверяют успех, 429/5xx, timeout, пустой/невалидный результат, конечность и отсутствие чувствительных значений; существующие клиентские сценарии проходят.

## Требования

- **FR-001:** Сохранить текущую модельную цепочку, prompts, формат запроса и OpenRouter-only реализацию.
- **FR-002:** Снять прикладные повторы provider/network ошибок в двух pipeline. Сохранять повтор только после HTTP 2xx с плохим содержимым.
- **FR-003:** Дедлайн рассчитывать от начала pipeline; `requestOpenRouter` получает остаток бюджета, завершает timeout безопасной ошибкой.
- **FR-004:** Преобразовывать provider/network ошибки в стабильное безопасное сообщение до логов, БД и клиента; diagnostics формировать по allowlist и строгим типам, без `...details`/`error.message`.
- **FR-005:** Спецификации, код, тесты и версия 1.1.4 входят в один коммит F04 после F03.

## Данные и доступ

Без миграций, новых API-полей, провайдеров и клиентских ключей. Форму `ok/data|error`, request ID и понятные сообщения сохраняем; состав диагностики намеренно сужаем по согласованию владельца. Production и локальные данные агент не меняет.

## Проверка

AC-1/2/4 — Node/Deno тесты с fake fetch/временем; AC-3 — negative assertions для диагностики и сообщений об ошибках; затем стандартные проверки проекта.
