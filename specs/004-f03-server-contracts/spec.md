## Результат и границы

Общая HTTP/Telegram/env-граница принимает только проверяемый JSON-объект там, где обработчик ожидает поля, сохраняет существующие публичные коды/форму ответа и server-only доступ к данным. `get-reading-history` (чтение) и `save-reading-position` (запись) показывают применение подхода. Другие Edge Functions и пользовательский контракт не переписываются.

## Сценарии и критерии

- **AC-1:** Некорректный JSON даёт текущий `400 INVALID_JSON`; корректный JSON другого типа (массив, `null`, примитив) даёт явную `400` ошибку объекта до Telegram/DB обращения.
- **AC-2:** Отсутствие `initData` и неверная Telegram-подпись по-прежнему отклоняются на сервере. Сервисный ключ не попадает в ответ.
- **AC-3:** Read/write образцы используют общий server-only клиент и lookup пользователя; успешные ответы и существующие ошибки данных имеют прежнюю форму и коды.
- **AC-4:** Deno-тесты проверяют HTTP-границу и типичные ошибки без реального Telegram, сети и БД; действующие проверки проекта проходят.

## Требования

- **FR-001:** Добавить runtime-проверку корневого JSON-объекта без небезопасного приведения `unknown` к типу; оставить общий `parseJsonBody<T>` для остальных обработчиков до их предметных фич.
- **FR-002:** Использовать проверенный объект в двух выбранных обработчиках и убрать их `@ts-nocheck`, если Deno typecheck это позволяет без изменения API или установки пакетов.
- **FR-003:** `get-reading-history` использует общий `createServiceClient`, а оба обработчика — `getAppUserByTelegramId`; service role остаётся только на сервере.
- **FR-004:** Ошибки обычного клиента сохраняют `ok/error`, HTTP status и согласованные сообщения; неожиданные ошибки не раскрывают SQL, токены и детали внутреннего провайдера.
- **FR-005:** Все спецификации и код F03 входят в один коммит с patch-версией после F02.

## Данные, доступ и эксплуатация

Миграций и изменений RLS нет. Запись позиции остаётся в прежней таблице и проверяет active text/индекс. Агент не запускает команды, меняющие БД.

## Проверка и открытые вопросы

AC-1/2/4 проверяются Deno-тестами общей границы; AC-3 — контрактными тестами и существующей проверкой типов/линтера. Новых продуктовых решений нет. Если снятие `@ts-nocheck` обнаружит широкий долг типов внешнего клиента, ограничить эту часть и зафиксировать отдельно, не менять внешний API ради typecheck.
