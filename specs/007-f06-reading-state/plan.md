## Решение и основания

Продолжить согласованный предметный серверный слой F05. Каждый из четырёх endpoints сохраняет отдельный HTTP-контракт и тонкую точку входа; типизированные сценарии состояния, позиции, завершения и истории используют узкий адаптер Supabase/RPC. Общие типы активного текста, ошибок чтения и учебной даты принадлежат модулю чтения. Не создавать универсальный CRUD-репозиторий; методы адаптера соответствуют операциям предметной области.

Сценарий состояния читает попытки и дневной completion для текущей учебной даты, активный текст без ограничения датой генерации и индексы слов только для этого текста. Позиция проверяет ID и границы абзацев до адресной записи; результат update защищён user ID и reading text ID. Завершение делегирует атомарность RPC complete_daily_reading_text, затем best-effort metrics. История сохраняет cursor по completed_at/id и действующий лимит.

## Контекст

F05 фиксирует контракт генерации и разделение HTTP/данных. F06 затрагивает get-reading-state/index.ts, save-reading-position/index.ts, complete-reading-text/index.ts, get-reading-history/index.ts, общие reading helpers и типы. Клиент ReadingScreen и MaterialsScreen потребляют ответы, но их UI не переписывается в F06. Схема, RLS и server-only функции не меняются.
