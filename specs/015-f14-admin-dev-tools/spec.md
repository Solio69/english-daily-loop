## Результат и границы

Администратор в разрешённой среде управляет восемью существующими локальными действиями через панель настроек. Панель и серверный endpoint имеют отдельные проверяемые части для интерфейса, входного контракта, авторизации и исполнения. Названия действий, выборки, порядок DB/RPC-операций, тексты и внешний вид сохраняются. Новые действия, production-конфигурация, миграции и изменение продуктовых правил не входят.

## Сценарии и критерии

- **AC-1:** Given `DEV_TOOLS_ENABLED` выключен, when поступает POST, then ответ `403 DEV_TOOLS_DISABLED` формируется до чтения секретов, авторизации и БД. Проверка: серверный тест.
- **AC-2:** Given флаг включён и Telegram `initData` проверена, when роль в БД `tester` или `user`, then ответ `403 DEV_TOOLS_ADMIN_REQUIRED` и ни одно действие с данными не вызвано; для `admin` разрешена диспетчеризация. Проверка: серверный тест с подставным DB-адаптером.
- **AC-3:** Given недопустимое имя действия или шаг повторения, when разбирается запрос, then ответ `400 INVALID_DEV_TOOL_ACTION` или `400 INVALID_REVIEW_STEP`; каждое из восьми допустимых действий направляется к своему обработчику. Проверка: контрактные тесты и тест диспетчеризации.
- **AC-4:** Given профиль `admin`, when открыты настройки, then доступна прежняя панель с восемью действиями; для `tester`/`user` панели нет. Во время вызова кнопки блокируются, успех обновляет профиль, ошибка показывает безопасный toast. Проверка: компонентный/браузерный тест.
- **AC-5:** Given ошибка БД или внутренняя ошибка, when endpoint возвращает ответ и пишет лог, then ответ не содержит токен, `initData` и детали БД; логи не содержат токен, `initData` и сырой DB error. Проверка: тест ошибок и ревью кода.

## Требования

- **FR-001:** Сервер обрабатывает только POST; `DEV_TOOLS_ENABLED === "true"` проверяется до `getRequiredEnv`, разбора тела и создания service client. Telegram `initData` проверяется только сервером.
- **FR-002:** Роль берётся из БД для аутентифицированного Telegram-пользователя; `assertAdminRole` завершается до исполнения любого действия. Клиентская видимость не считается защитой endpoint.
- **FR-003:** Входной контракт типизирован: имя ровно одного из восьми действий; `reviewStep` обязателен только для `complete_today_vocabulary_reviews_at_step`, остальные поля не меняют семантику действий.
- **FR-004:** Диспетчеризация сопоставляет каждое имя с прежним обработчиком. Существующие таблицы, фильтры, study date, RPC-параметры, возвращаемые поля и порядок операций сохраняются.
- **FR-005:** Клиентский сервис инкапсулирует вызов endpoint; панель отвечает за отображение и ввод. Сохраняются вид, русские подписи, разворачивание, блокировка на время вызова и toast-сообщения; после успеха профиль обновляется.
- **FR-006:** Ошибки имеют безопасные коды/сообщения; server logs содержат диагностический этап/код без секретов, `initData`, сырых DB messages и персональных идентификаторов.
- **FR-007:** Миграций, изменения RLS/grants, новых зависимостей и команд агента для изменения данных БД нет. Тесты используют только подставные адаптеры.

## Данные, доступ и эксплуатация

Endpoint использует текущий `SUPABASE_SERVICE_ROLE_KEY` только на сервере и существующие таблицы попыток, словаря, завершений чтения и подписок. RPC `dev_complete_vocabulary_reviews_at_step` остаётся server-only. Флаг `DEV_TOOLS_ENABLED` — обязательная серверная преграда; роль `admin` — вторая преграда. Production-конфигурация и БД не затрагиваются. Действия вручную в ходе реализации агент не запускает.
