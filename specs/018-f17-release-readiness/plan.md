## Технический подход

F17 не вводит новый слой приложения. Проверяются контракты между Telegram Mini App, клиентскими сервисами, Edge Functions и Postgres. Ручная проверка в dev-боте дополняет автоматические тесты там, где фикстуры не заменяют реальный Telegram initData, bot/webhook и пользовательские роли.

Автоматические проверки выполняются на одном финальном состоянии ветки. Обычная сборка пишет в dist; build:telegram — в dist-telegram, который использует запущенный dev-stack, поэтому её запуск откладывается до остановки dev-stack владельцем. Замер JS/CSS фиксируется вместе с предупреждениями Vite. Порог чанка не повышается ради зелёного вывода.

Анализ доступности использует существующие Playwright-сценарии и ручной просмотр мобильных экранов/клавиатуры. После проверки контраста владелица попросила вернуть исходные цвета. Четыре светлых токена восстановлены; владелица явно приняла прежние сочетания с контрастом ниже 4,5:1 как ограничение 1.1.17. Соответствие AC-3 по контрасту не заявляется. Тёмная тема не менялась. Для безопасности сверяются текущие auth, RLS/grants, сканирование tracked-файлов на секреты и порядок миграции/Edge. Агент не запускает изменяющие DB-команды. Если нужна новая автоматизация, не входящая в согласованный набор инструментов, сначала возвращается к владельцу.

## Релизные артефакты

Версия кандидата 1.1.17 согласована. package.json задаёт версию; pnpm-lock.yaml не содержит версии импортера и не меняется; currentRelease показывает только короткие пользовательские изменения последней версии, а CHANGELOG хранит техническую историю. Дату ставить по фактическому дню публикации, при изменении даты повторить release:check и затронутые проверки.

Обновить ссылки AGENTS/constitution на реальные work/agents, сводку изменений релиза и инструкцию обновления существующего production. Не переписывать исторические решения без подтверждённых фактов. В частности, текущий Vercel SHA и production migration history ещё не установлены.

## Риски и передача

Production 1.0.0 обслуживает реальных пользователей. До migration необходимы подтверждённые production SHA/history, dry run, свежий snapshot и план остановки при расхождении; порядок: миграция → postcheck → Edge Functions → frontend/merge → Telegram smoke. Последний recovery drill относится к старому snapshot; по решению владельца новый drill пропущен, поэтому работоспособность восстановления свежего snapshot не доказана. Тег и GitHub Release возможны только после успешного smoke.
