## Результат и границы

Генерация текста — существующий серверный сценарий. Вызов проверяет Telegram initData, загружает настройки и effective access, учитывает попытку, обращается к OpenRouter, проверяет текст и сохраняет активный результат. Код сценария разделён на HTTP-границу, предметную логику, AI-адаптер и доступ к данным с явными типами. Пользовательское поведение, модельная цепочка, prompt, правила текста, ошибки и публичные поля ответа сохраняются.

Входит только серверная генерация. Состояние, позиция, завершение и история — F06; клиентский сценарий — F07; словарь — F08. Новых миграций, зависимостей и изменений схемы не требуется. Если они окажутся необходимы, это новое решение владельца.

## Сценарии и критерии

- **US-1:** Пользователь с доступной попыткой получает текст по своим настройкам и видит прежний счётчик.
- **AC-1:** Given валидный Telegram initData, настройки и свободный дневной лимит, when приходит новый request ID, then одна попытка учитывается на московскую учебную дату; после валидного AI-ответа активный текст и успешная попытка сохраняются атомарно, а ответ содержит прежние text, generation, dailyLimit, usedAttempts и remainingAttempts.
- **AC-2:** Given request ID уже учтён, when тот же запрос приходит повторно, then лимит не списывается второй раз и AI-вызов не повторяется; завершённый результат возвращается, пока он остаётся активным, а обработка незавершённого/замещённого/неуспешного запроса сохраняет действующие коды и безопасные ответы.
- **AC-3:** Given дневной лимит исчерпан, when приходит новый request ID, then AI не вызывается и возвращается действующая ошибка лимита.
- **AC-4:** Given OpenRouter вернул отказ, пустой или предметно невалидный ответ, when генерация не может завершиться, then невалидный текст не становится активным; статус попытки и безопасная диагностика соответствуют действующему контракту F04. Невалидное содержимое может повторяться только в действующем конечном бюджете F04.
- **AC-5:** Given отказ обновления metadata или финального RPC, when запрос завершается, then публичный ответ остаётся безопасным; сохранение текста и успешной попытки не расходится. Повтор финального RPC ограничен действующим числом попыток.
- **AC-6:** Given отсутствие или неверная подпись Telegram initData, when вызывается endpoint, then защищённые данные не читаются и AI не вызывается; service role key, bot token, prompt, сырой ответ провайдера и лишние пользовательские данные не попадают в клиентский ответ и логи.

## Требования

- **FR-001:** Сохранить endpoint generate-reading-text, метод POST, CORS, форму ok/data или error, request ID и прежние публичные поля/коды.
- **FR-002:** Сохранить значения уровня A1/A2/B1/B2, длительности 3/5/10/15 минут, действующие диапазоны слов, критерии валидации, prompt version, модельную цепочку и бюджеты F04.
- **FR-003:** Выполнять claim через действующую server-only RPC claim_reading_generation_request с неизменными правилами подсчёта всех попыток и уникальностью user ID + request ID.
- **FR-004:** Выполнять finish через действующую server-only RPC finish_reading_generation_request; активный текст и статус succeeded фиксируются атомарно.
- **FR-005:** Разделить HTTP, сценарий, предметную генерацию и Supabase/RPC-адаптер. Внешние DB/RPC JSON проверять на границе до использования; зависимости сценария выражать узкими типами.
- **FR-006:** Сохранить безопасную диагностику F04, права доступа, ошибки и отсутствие прямой записи клиента в защищённые таблицы.

## Данные, доступ и эксплуатация

Используются существующие user_settings, reading_generation_attempts и user_active_reading_texts. Доступ к защищённым таблицам и RPC остаётся server-only через service_role после проверки Telegram initData. Схема, RLS, grants, backup/recovery contract и production данные не меняются. Agent не запускает команды изменения БД. Rollout следует обычному порядку Edge Function и frontend без совместимого изменения API.
