# Security threat model

## 1) Назначение
Этот документ фиксирует базовую модель угроз для MVP.
Он нужен, чтобы проверять безопасность не абстрактно, а по конкретным рискам проекта.

Проект - Telegram Mini App на Vite + React + TypeScript.
Backend-граница сейчас проходит через Supabase Edge Functions, Postgres и RPC.

## 2) Что защищаем

### Секреты и ключи
Критичные секреты не должны попадать во frontend, git, публичные логи или ответы API:
- `SUPABASE_SERVICE_ROLE_KEY`
- `TELEGRAM_BOT_TOKEN`
- `OPENROUTER_API_KEY`
- реальные production-секреты и токены

Во frontend допустимы только переменные с префиксом `VITE_`, если они не являются секретами.

### Данные пользователя
Пользователь должен иметь доступ только к своим данным:
- профиль в `public.users`
- настройки в `public.user_settings`
- активный текст
- история прочитанных текстов
- дневной прогресс
- подписки

Нельзя доверять `user_id`, `telegram_user_id` или другим идентификаторам, если они пришли из body запроса.
Текущий пользователь должен определяться на сервере из валидного Telegram `initData`.

### Лимиты и подписки
Frontend может отображать лимиты и тарифное состояние, но не должен принимать решения доступа.

На сервере должны проверяться:
- free/paid состояние
- дневной лимит генераций
- списание попыток генерации
- завершение активного текста
- активация или планирование подписки

Критичные операции должны оставаться атомарными, особенно при параллельных запросах.

### AI-ресурсы и стабильность генерации
AI-пайплайн должен защищать:
- `OPENROUTER_API_KEY`
- дневные лимиты генерации
- состояние активного текста
- приложение от зависаний и неконтролируемых ошибок внешнего provider
- пользователя от невалидного ответа модели
- приложение от prompt leakage, HTML/script output и неподдерживаемых provider-моделей

В модель нельзя отправлять секреты, полный Telegram `initData` и лишние пользовательские данные.
Модель и provider считаются недоверенными: сервер валидирует output до сохранения в БД.

## 3) Кого считаем атакующим
Для MVP основной атакующий - обычный пользователь приложения, который может:
- открыть DevTools
- посмотреть frontend bundle
- вызвать Edge Function напрямую через curl/Postman
- изменить body запроса
- повторять запросы много раз или параллельно
- попробовать использовать старый, чужой или поддельный Telegram `initData`
- попробовать вызвать Supabase REST/RPC напрямую через anon key

Из этого следует базовое правило: frontend является недоверенной зоной.

## 4) Основные точки входа

Edge Functions:
- `auth-telegram`
- `save-user-settings`
- `get-reading-state`
- `generate-reading-text`
- `complete-reading-text`
- `get-reading-history`
- `activate-subscription`
- `dev-tools`

Другие входы:
- frontend Supabase client
- прямой доступ к Supabase REST/RPC через anon key
- OpenRouter как внешний AI-provider

## 5) Базовые правила защиты
- Telegram `initData` проверяется только на сервере.
- Все чувствительные Edge Functions должны валидировать `initData`.
- Текущий пользователь определяется из валидного `initData`, а не из body.
- Все входные параметры из клиента проходят allowlist/range validation.
- Frontend не пишет напрямую в защищенные пользовательские, reading и subscription таблицы.
- Лимиты, подписки и дневной прогресс считаются на сервере.
- Критичные DB-операции выполняются через RLS/grants и транзакционные RPC.
- Dev tools должны быть закрыты server env флагом, а не только frontend UI-флагом.
- Ошибки клиенту возвращаются без секретов, stack trace и SQL/provider details.
- Логи не должны содержать секреты, полный `initData` или чувствительные ключи.
- AI observability хранит только metadata попытки; полный prompt, raw provider response, полный generated text и stack trace не пишутся в `reading_generation_attempts`.

## 6) Abuse cases для проверки
- Пользователь подменяет `telegram_user_id` или `user_id` в body.
- Пользователь пытается получить историю чтения другого пользователя.
- Пользователь пытается сохранить настройки другому пользователю.
- Пользователь пытается сгенерировать больше текстов, чем позволяет дневной лимит.
- Пользователь отправляет несколько параллельных запросов генерации.
- Пользователь пытается завершить чтение без активного текста.
- Пользователь пытается активировать paid-состояние некорректным `planType`.
- Пользователь пытается вызвать `dev-tools` при выключенном server env.
- Пользователь пытается выполнить опасный RPC напрямую через anon key.
- AI-provider возвращает невалидный JSON, неправильную длину текста или ошибку.
- AI-provider возвращает HTML/script, markdown code fence, prompt leakage или модель вне allowlist.
- Ошибка OpenRouter не должна повреждать текущий активный текст.
- Ошибка OpenRouter не должна записывать в БД raw provider response, полный prompt или stack trace.
- Секреты не должны попадать в frontend bundle, git, ответы API или логи.

## 7) Чеклист дальнейшего аудита
1. Секреты и frontend env.
2. Клиентский сервисный слой.
3. Edge Functions auth и input validation.
4. Business logic abuse: лимиты, подписки, чтение.
5. Postgres RLS, policies и grants.
6. Postgres RPC: права, `search_path`, атомарность, advisory locks.
7. Dev tools и debug flags.
8. AI pipeline security.
9. Логи и формат ошибок.
10. Production readiness.
