# Production-релиз 1.0.0

Статус: локальная подготовка завершена; ожидает ручной production rollout.

## Цель и результат

Production Telegram Mini App работает на едином релизном контракте версии
`1.0.0`. Пользователь может открыть приложение через production-бота, продолжить
учебный сценарий и воспользоваться функциями текущей ветки. После успешного
smoke фиксируются production commit, версия, миграции, результат проверки и
точка остановки проекта.

## Состав релиза

- В релиз входит вся ветка `feat/error-report-processing` относительно
  production-основы `main` (`bb90b2b2fa0bf797a27ebd0c251e1827f9eb3469`).
  На момент подготовки документа это восемь коммитов от `38b7a84` до
  `248cdfb`; итоговый commit фиксируется после подготовки release metadata и
  перед production rollout.
- Пользовательские изменения: onboarding и справка production-бота,
  приветствие на главной в рамках сессии, сохранение серии чтения до
  пропущенного учебного дня, удаление ожидающего слова из активного текста.
- Серверные изменения: обработка Telegram webhook, безопасная обработка
  диагностик support report, Edge Function удаления ожидающего слова и
  атомарная подготовка карточек.
- Операционные изменения: диагностика ранних ошибок production backup и
  связанные backup/recovery contracts.
- Новые migration-файлы релиза:
  `20260813120000_add_pending_vocabulary_word_deletion.sql` и
  `20260813150000_add_atomic_vocabulary_card_persistence.sql`.
- Версия `1.0.0` отражается в `package.json`, `src/constants/currentRelease.ts`
  и `CHANGELOG.md`. Дата в release metadata — календарная дата фактического
  выпуска; целевая дата текущего rollout — `2026-09-25`. Если выпуск переносится
  на другой день, дата уточняется до финального release commit и повторного
  локального preflight.

Пункты «Что нового» для пользователя:

1. «Бот помогает начать занятия и подсказывает, как открыть приложение.»
2. «Главная приветствует с учётом текущей сессии.»
3. «Серия чтения сохраняется, пока не пропущен учебный день.»
4. «Ожидающее слово можно удалить прямо из текста до подготовки карточки.»

В scope не входят новые продуктовые функции, новые миграции, изменение
платформы `Supabase Cloud + Vercel`, автоматизация production deploy,
contract cleanup персональных данных и оптимизация размера JS-бандла.

## Пользовательский и технический flow

1. Владелец выпускает согласованный commit ветки через действующий ручной
   production runbook. До публикации нового frontend production продолжает
   обслуживать текущую версию приложения.
2. Новая схема предоставляет только `service_role` две server-only RPC:
   удаление ожидающего слова и атомарное сохранение AI-карточки. Вызовы из
   Mini App проходят через Edge Functions с серверной проверкой Telegram
   `initData`; прямой доступ `anon` и `authenticated` к RPC закрыт. Обе
   миграции определяют функции и grants, не переписывая существующие строки
   пользовательских таблиц.
3. После проверки схемы разворачиваются совместимые Edge Functions, затем
   frontend из того же release commit и настройки production-бота.
4. Пользователь открывает Mini App в Telegram, проходит auth, продолжает
   чтение и работу со словами. Ошибки показываются без секретов и внутренних
   деталей, а support report содержит только безопасные диагностические поля.
5. В настройках версия `1.0.0` и «Что нового» описывают опубликованный релиз.

## План подготовки агентом

1. Обновить version в `package.json` до `1.0.0`; зависимости и lockfile не
   менять без причины.
2. Подготовить дату и 1–5 понятных пользователю пунктов в
   `src/constants/currentRelease.ts`.
3. Оформить секцию `1.0.0` в `CHANGELOG.md` по фактическому составу ветки;
   оставить пустую секцию `Unreleased` для дальнейшей работы.
4. Уточнить `notes/backup-and-restore.md`: для pre-release full-service drill
   разворачивается зафиксированный release candidate, а для регулярного drill —
   текущий production commit. В обоих случаях SHA опубликованного production
   deployment, SHA проверяемого runtime и snapshot id записываются в evidence.
   Уточнить устаревший release scope в
   рабочей папке проекта. Описывать актуальное состояние без формулировок
   истории изменений.
5. Выполнить `pnpm release:check`, `pnpm lint`, `pnpm test`, `pnpm build`,
   `pnpm build:telegram`, `git diff --check` и pre-commit review. Проверить
   соответствие этой спецификации. Git-изменения выполняет только владелец.

## Ручной production rollout владельца

Общий порядок и безопасное обращение с секретами задаёт
`notes/production-deploy-flow.md`. Этапы выполняются последовательно и по одной
команде за шаг при совместной отладке.

1. Зафиксировать итоговый release commit и убедиться, что он содержит всю
   согласованную ветку, версию `1.0.0` и чистое рабочее дерево. Проверить
   доступность production-сервисов и актуальность environment inventory.
2. Подтвердить завершённый pre-migration snapshot и штатный backup status.
   Проверка `2026-09-25` подтвердила snapshot
   `2026-09-24T150003Z_3c4847d4` с
   `latestMigrationVersion = 20260731120000`; фактический последний snapshot
   и его свежесть проверяются снова непосредственно перед действием с БД.
3. Сверить реальную production migration history и dry-run с ровно двумя
   согласованными migration-файлами в указанном порядке. Если history или SQL
   расходятся, остановить rollout. Миграции применяет только владелец по
   отдельно проверенной operational-процедуре; эта спецификация не содержит
   исполняемых команд изменения production БД.
4. Провести read-only postcheck функций, прав `service_role`, запрета execute
   для `anon`/`authenticated`, RLS и database logs. Старый runtime должен
   продолжать работать с расширенной схемой.
5. Создать новый completed snapshot с migration version `20260813150000` и
   провести isolated recovery drill по `notes/backup-and-restore.md`.
   Read-only DB validation подтверждает восстановление обеих новых RPC и
   server-only grants. Full-service smoke использует release candidate commit
   в отдельном recovery project, отдельного development bot и recovery
   frontend; production Vercel и production bot не меняются. При неуспехе
   дальнейший rollout остановить.
6. Проверить server-only secrets без вывода значений, развернуть Edge
   Functions из release commit и проверить их startup/runtime logs.
7. Опубликовать Vercel frontend из того же commit, сверить build SHA,
   `appVersion = 1.0.0` и production Supabase URL. Настроить production-бота
   по runbook без передачи token или webhook secret в аргументах и логах.
8. Выполнить ручной Telegram smoke по
   `notes/production-smoke-checklist.md`. При `fail` не создавать tag или
   GitHub Release; исследовать ошибку и выбрать совместимый forward-fix.
9. При `pass` владелец фиксирует evidence и создаёт tag `v1.0.0` и GitHub
   Release для фактического production commit. Зафиксировать точку остановки
   проекта в задаче выпуска.

## Критерии приёмки и ручная проверка

- Локальные проверки из плана подготовки прошли; release metadata показывает
  одну версию и дату. Рабочее дерево перед rollout чистое.
- Production migration history содержит ожидаемые версии без посторонних
  pending миграций; обе RPC доступны `service_role` и недоступны клиентским
  ролям. Новый snapshot валиден, recovery drill завершился успешно.
- Production Vercel deployment и Edge Functions соответствуют одному release
  commit. Telegram webhook отвечает на `/start`, `/help` и обычный текст;
  кнопки открывают production Mini App.
- В Telegram проверить auth и настройки нового пользователя; главную,
  генерацию и завершение текста, материалы, сохранение и подтверждаемое
  удаление pending-слова, подготовку готовой карточки и повторение.
- Убедиться, что удаление pending-слова снимает все его подсветки после
  успешного ответа сервера; подготовленная карточка не удаляется этим flow.
- Проверить отображение серии и прогресса существующего пользователя, а также
  приветствие при повторном открытии сессии. Граничные переходы учебных дней
  покрываются автоматическими тестами, без ожидания смены дня в production.
- Проверить отправку support report, безопасный состав diagnostics, версию
  `1.0.0`, дату и «Что нового»; сверить `buildId` с Vercel Git SHA.
- Проверить роли, отсутствие прямого клиентского доступа к защищённым данным,
  основные светлую/тёмную темы и навигацию. Результат и известные ограничения
  записать в smoke checklist.

## Риски и условия остановки

- Несовпадение production migration history с текущим snapshot или dry-run,
  неожиданный SQL, права клиента на server-only RPC либо ошибка применения
  миграций останавливают rollout до анализа. Схема production не откатывается
  вручную без отдельного плана.
- Отсутствие нового snapshot или успешного recovery drill для расширенного
  контракта блокирует deploy нового runtime.
- Ошибки Edge Functions, отсутствие нужных secrets, неправильный Vercel SHA
  или провал Telegram smoke блокируют tag и GitHub Release.
- `1.0.0` является согласованной версией выпуска; фактическая готовность
  подтверждается только пройденными проверками и production smoke.

Открытых продуктовых и архитектурных решений нет. Действия с production БД,
backup, restore, deployment и Git выполняет владелец проекта.
