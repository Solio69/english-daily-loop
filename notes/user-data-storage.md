# Хранение пользовательских данных

## Назначение

Документ фиксирует минимальный состав пользовательских данных English Daily Loop, цели хранения и ограничения их передачи между слоями приложения.

## Профиль и идентичность

- `public.users.id` — внутренний идентификатор для связей таблиц, server logs и support diagnostics.
- `public.users.telegram_user_id` — server-only идентификатор для Telegram auth и будущих сообщений через Bot API.
- `public.users.first_name` — отображаемое имя для персонального приветствия.
- роль, onboarding-флаги и timestamps нужны для доступа и состояния приложения.
- `username`, `last_name` и `language_code` приложением не собираются. Nullable-столбцы остаются в схеме до отдельного contract cleanup.

Frontend получает внутренний `id`, роль, `firstName`, настройки и прогресс. Прямой Telegram ID во frontend user contract не передается.

## Настройки и учебные данные

- `public.user_settings` хранит уровень английского и выбранное время чтения.
- reading-таблицы хранят активные и завершенные тексты, дневной прогресс и позицию чтения.
- vocabulary-таблицы хранят слова, карточки, источники и состояние повторения.
- subscription-таблица хранит состояние MVP-подписки.

Эти данные доступны клиенту только через Edge Functions. Прямой доступ `anon` и `authenticated` к защищенным таблицам и server-only RPC закрыт.

## Диагностика

- Support report хранит внутренний `user_id`, роль, комментарий, экран, безопасный app context, последние client events, request ids и safe AI diagnostics.
- Новые support reports не содержат прямой Telegram ID ни в отдельном значении, ни в `app_context`.
- AI attempt metadata содержит модель, prompt version, диапазоны валидации, длительность и безопасную стадию ошибки.
- Client diagnostic buffer хранится в `sessionStorage` текущей browser-сессии и отправляется только по явному действию пользователя.

В автоматически собранные support diagnostics, frontend state и прикладные логи запрещено добавлять:

- Telegram `initData` и прямой Telegram ID;
- bot token, service role key, OpenRouter key и другие secrets;
- полный prompt, raw AI response и полный generated text;
- stack trace, полный `process.env`, пароли и контактные данные.

Для корреляции используются `requestId`, внутренний `appUserId`, report id и attempt id.

Пользовательский комментарий является отдельным свободным текстом: приложение не может гарантированно удалить из него добровольно введенные личные данные. Риск ограничивается предупреждением в UI, ручной отправкой отчета и retention `30` дней.

## Передача во внешние сервисы

- OpenRouter получает только учебные данные, необходимые конкретной генерации, без идентификаторов и профиля пользователя.
- Telegram Bot API в будущих сценариях может использовать server-side `users.telegram_user_id`.
- Support diagnostics не отправляются автоматически и остаются в server-only таблице.

## Сроки хранения

- Профиль, настройки и учебные данные хранятся, пока существует аккаунт.
- Support reports хранятся `30` дней и удаляются job `cleanup_support_reports`.
- Metadata AI-попыток хранится `90` дней и удаляется соответствующими cleanup jobs.
- Client diagnostic buffer живет до окончания browser-сессии.
- Retention platform logs определяется настройками Supabase; приложение не пишет в них прямой Telegram ID.
- Локальные production snapshots хранятся по правилу `7` последних завершенных копий плюс по одной последней копии за каждую из `4` завершенных ISO-недель.

## Данные в backup

- Logical snapshots хранятся на компьютере владельца вне репозитория.
- Snapshot содержит production-схему и пользовательские данные, но не должен содержать application secrets, database password или Telegram/OpenRouter tokens.
- Незашифрованное хранение временно принято владельцем с риском чтения данных при доступе к компьютеру или диску.
- Папка ограничивается текущим Windows-пользователем и `SYSTEM`, не синхронизируется в публичное облако и не коммитится.
- Шифрование и отдельная offsite copy остаются следующими улучшениями.
- Актуальные путь, retention и процедура восстановления описаны в `notes/backup-and-restore.md`.

## Ограничения MVP

- Self-service удаление аккаунта и каскадное удаление данных не реализованы.
- Экспорт пользовательских данных и отдельный privacy-раздел в UI не реализованы.
- Пользователь может самостоятельно указать личные данные в комментарии к отчету; UI предупреждает этого не делать, а отчет отправляется только вручную и хранится `30` дней.
- Физическое удаление совместимых столбцов выполняется отдельным contract cleanup после успешного production rollout runtime-контракта, свежего completed snapshot и успешного recovery drill.

Удаление аккаунта и экспорт данных требуют отдельных согласованных продуктовых спецификаций.
